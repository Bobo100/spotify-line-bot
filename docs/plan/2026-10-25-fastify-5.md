# 升級 fastify 到 5

- 日期：2026-10-25
- Branch：`claude/fastify-5`
- PR：#8

## 背景

fastify 4 有 16 個安全性警告（`fastify` 15 個、`find-my-way` 1 個），修正版只在 fastify 5。PR #6 只做了不跨 major 的更新，所以這些警告還在。

Dependabot 開了 PR #7，只把 `fastify` 本體升到 5.12.6。實測後發現 `@fastify/cookie` 9.x 和 `@fastify/mongodb` 8.x 只支援 fastify 4，註冊時會報 `FST_ERR_PLUGIN_VERSION_MISMATCH`。app 一啟動就要註冊這兩個外掛，所以 merge #7 之後每個請求都會失敗。type-check 和 Vercel 的檢查都不會實際啟動 app，看不出這個問題。

## 計畫

- [x] 升級套件：
  - `fastify` → ^5.12.7
  - `@fastify/cookie` → ^11.1.3
  - `@fastify/mongodb` → ^9.0.2（支援 fastify 5，MongoDB driver 維持 6.x；10.x 會連 driver 一起升到 7，不在這次範圍）
- [x] 移除程式碼沒用到的 `fastify-cli`、`fastify-plugin`（`fastify-cli` 5 會在 lockfile 留一份 fastify 4）
- [x] 對照 fastify 5 和 `@fastify/cookie` 11 的破壞性變更，檢查程式碼
- [x] 驗證：type-check；實際註冊外掛；用 Fastify 實際送請求跑過 webhook、登入、callback 的 cookie 流程；Vercel preview 部署
- [x] 關掉 PR #7（留言說明由 #8 取代）

## 實際改動

- `package.json`：
  - `fastify` ^4.0.0 → ^5.12.7（實際安裝 5.12.7）
  - `@fastify/cookie` ^9.2.0 → ^11.1.3
  - `@fastify/mongodb` ^8.0.0 → ^9.0.2；MongoDB driver 維持 6.21.0
  - 移除 `fastify-cli`、`fastify-plugin`：程式碼和 scripts 都沒用到（`dev` 用的是 `nodemon` + `ts-node`）
  - PR #6 加的 `resolutions` 不變
  - `description` 原本寫「由 Fastify-CLI 建立」，移除 `fastify-cli` 後改成專案說明
- `yarn.lock`：用 `yarn add` / `yarn remove` 重新產生，lockfile 裡已經沒有 fastify 4；其他執行時會用到的套件（`mongodb`、`axios`、`@line/bot-sdk`、`dotenv`、`lodash`、`undici`）版本都沒變
- 程式碼不用改：對照 fastify 5 的破壞性變更，`reply.redirect` 只傳網址（v5 改了參數順序，不影響）、外掛是同步函式搭配 `done`、`listen` 用物件參數、`logger: true`，都沒用到被移除的 API

## 和計畫不同的地方

- code review 後：`package.json` 的 `description` 還寫著由 Fastify-CLI 建立，順手改掉
- 計畫寫的「Vercel preview 部署」只確認到 build 和部署成功；這個環境的網路規則擋住 `vercel.app`，沒辦法實際打 preview 的 API

## 驗證

- `npx tsc --noEmit` 通過
- 用真的 fastify 5.12.7 + `@fastify/cookie` 11.1.3，把 app 的所有 route 掛起來實際送請求，10 項全部通過；同一支測試在 main（fastify 4.29.1 + cookie 9.4.0）上結果完全一樣：
  - app 能啟動、`GET /webhook/` 回 200
  - 簽章正確的 webhook 送 `login` → 回 200，LINE 回覆有登入連結；簽章錯誤 → 401
  - `/spotify/login` → 302 到 Spotify，帶 `state`，設定 3 個簽章 cookie（HttpOnly、Secure、SameSite=Lax、10 分鐘）
  - `/spotify/callback`：`state` 錯誤 → 400；cookie 被竄改 → 400；正確 → 存下 token 和 Spotify user id，清掉 cookie
  - `/search` 回 200；`POST /playlist/add` 的 JSON body 能解析，無效 position 回 400
  - MongoDB、Spotify、LINE 都用假的替身
- 真的 `@fastify/mongodb` 9 可以通過 fastify 5 的版本檢查（測試環境沒有資料庫，只會出現連線錯誤）
- `@fastify/cookie` 9 簽的 cookie 在 11 上驗得過，反過來也可以：部署交接時正在登入的使用者不會失敗，要退版也安全
- `yarn audit`：漏洞從 51 個降到 31 個（Critical 1、High 24 → 12），`fastify`（9 個）和 `find-my-way`（1 個）的警告全部消失
- `@fastify/cookie` 11 是在執行時用動態 `import('cookie')` 載入只支援 ESM 的 `cookie` 2.x。用 Vercel 打包用的 `@vercel/nft` 追蹤，確認 `node_modules/cookie/dist/index.js` 會被包進 function
- Vercel preview（`spotify-line-bot-git-claude-fastify-5-bobo100-project.vercel.app`）build 和部署成功
- code review + 對抗性驗證：沒有確定的 bug；6 項意見中 2 項已處理（動態載入已驗證、`description` 已修），紀錄空段落已補齊，3 項不處理（原因見下）
- 尚未實際打 preview 的 API（網路被擋），也尚未在真的 LINE 上實測

## 影響與注意事項

- 不需要新的環境變數，也不需要重新登入
- 行為沒有改變；merge 後 LINE 上有異常，先查 fastify 5 的請求處理和 `@fastify/cookie` 11 的 cookie 解析
- 剩下的 `@fastify/busboy` 警告來自 `@vercel/node` 底下的 `undici`，跟 fastify 本身無關（PR #6 的紀錄已列出）

## code review 中不處理的項目

- 「沒用到的 `tap`、放在 `dependencies` 的開發工具（`ts-node`、`nodemon`、`typescript`、`@types/*`）也該一起整理」：跟 fastify 升級無關，依「一個 PR 只做一件事」另外處理
- 「LINE 簽章是對 `JSON.stringify(request.body)` 驗證，不是原始 body」：既有問題，不是這次升級造成的
- 「`api/serverless.ts` 載入時就呼叫 `app.listen`，失敗會 `process.exit(1)`」：既有問題，不是這次升級造成的

## 後續待辦

- 整理相依套件：移除沒用到的 `tap`（`lodash` 目前靠它才裝得到，要先把 `lodash` 加進 `dependencies`），把開發工具移到 `devDependencies`
- webhook 簽章改成對原始 body 驗證：LINE 送來的 JSON 如果有跳脫字元（例如 `\u3042`）或不同的空白，`JSON.stringify` 重組後會不一樣，可能把正常的訊息當成簽章錯誤
- `api/serverless.ts` 不要在載入時就 `listen`：本機開發和 Vercel 的進入點分開
